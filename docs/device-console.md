# The firmware and the USB console

Code: `device/main.cpp` (the wiring and the loop), `src/board/Console.{h,cpp}`, `device/Esp32UsbPort.h`, `device/Sleep.h`, `device/ShippedCatalogs.h` with the generated `device/ShippedAssets.h`; tools `scripts/deviceconfig.py` and `scripts/webbridge.py`; tests in `test/test_console/`, `test/test_device_tools/test_tools.py` and `test/test_runtime/`.

## The wiring

`device/main.cpp` builds the capabilities of the board and hands them to `boot::Runtime` exactly as `sim/main.cpp` hands it the fakes: the clock (`DeviceClock`), power (`BoardPower`), the modem (`A7682EDriver` on `ModemTransport`), the receiver (`BoardGnss`), vibration (`BoardHaptic`), the log (`SdEventLog`), the card's store (`SdConfigStore`), Wi-Fi and the TCP server, the page from the flash, the display and, optionally, the motion sensor. The history's file (`SdMessageLog`) goes in through `Capabilities::messageLog`, attached before the core starts, so the history is read back after a restart. The radio is not handed over: `RadioLink` has no implementation here, the core has no radio and its tile is off.

The start is in this order: the board (expander, resets), the one SPI bus, the card (mount, recovery of an interrupted write), the configuration (read once for the modem's APN and PIN and the battery size; the runtime reads it again), the modem, power and receiver objects, the fuel gauge's capacity check, the keyboard, the touch chip, the UARTs, the display, the catalogs, the runtime, and last the cellular domain on.

**The loop** does what only hardware can: the card's retry and the log's backlog, the console, the keyboard and the touch into `Runtime::input`, the modem's state machine and its log lines, the network and satellite times into `TimeSync`, the vibration pulses, one `Runtime::step`, and then the runtime's requests:

- a request to **start the radio** is answered with "not available" (one log line);
- a request to **switch off** shuts the modem down first (it says goodbye to the network, up to ten seconds), then `BoardPower::powerOff()`, which refuses while a cable feeds the board;
- a request to **restart** restarts the processor;
- the power logic's decision on **sleeping** is carried out as light sleep that wakes on the timer, a key, a touch or the modem's ring line; **nothing sleeps while a cable is attached** (the policy's rule 6), because the USB bridge is off in light sleep.

The shipped catalogs and the version are data of the firmware (`ShippedAssets.h`, generated by `scripts/gen_device_assets.py` from `lang/` and `VERSION`; CI checks that it is current). PlatformIO's `embed_txtfiles` cannot hold them because it names objects after the file name alone and `lang/en.toml` and `lang/web/en.toml` collide.

## The console

The console is the processor's own USB port. Lines (each also with the word `CONFIG` in front):

| Line | Does |
|---|---|
| `CONFIG LIST` | the files in `/config` with their sizes |
| `CONFIG READ <file>` | the file between `CONFIG CONTENT …` and `CONFIG END` (of a long log the last 8 KB, with where they start) |
| `CONFIG WRITE <file> <n> <sum>` | answers `CONFIG READY n`, takes `n` raw bytes, checks the 16-bit sum, writes through the card's safe write; `CONFIG OK <file> <n>` |
| `CONFIG RESTART` | `CONFIG OK restart`, then restarts |
| `CONFIG WEB <n>` | the bridge to the parents' page: `n` bytes of an HTTP request in, `CONFIG WEB <m>` and `m` bytes out; the same checks and the same password as over Wi-Fi |
| `BATTERY` | the diagnosis of the fuel gauge and the charger (reads, writes nothing), between `CONFIG BATTERY BEGIN` and `END` |
| `SMS <number> <text>` | sends a text by hand the way the screens do (`\n` is a line break) |

**Over the cable only the known files are reachable**: `settings.toml`, `contacts.toml` and `secrets.toml` can be read and written, `system.log`, `system.old.log`, `messages.log`, `energy.log` and `energy.old.log` read. No path, no `..`, nothing else. A line longer than 320 bytes is refused once and its tail is not run as a command; raw bytes that do not arrive within ten seconds are given up with a message; a length or checksum that is not a plain number in range is refused. Lines that are not commands (the device's own log lines) are ignored. The console never blocks: it takes what has arrived and returns.

**The console asks for no password** (decision D-28). Whoever has the device on a cable can read the files the list above names, `secrets.toml` among them, write them, restart the device and send a text in the child's name; the only line with a password is `CONFIG WEB`, which carries the page's. The console is the owner's tool for a device on the desk, and the risk is a computer the child plugs the device into elsewhere. The user's guide says so in its three languages. Whether the console should answer only while the device is unlocked, or only in the first minutes after a start, is open point 33.

**Opening the serial port resets the ESP32** (the USB bridge restarts it), which is why a tool that reads the logs restarts the device. The console needs no port to be opened to work: the firmware sets the transmit timeout to zero, so output that nobody takes is dropped instead of waited for, and the tools wait three seconds after opening the port for the device to come back.

**Long answers and the transmit buffer (seen on the device 2026-10-07, firmware 4.0.0; fix host-tested, not yet verified on the device).** With the transmit timeout at zero, `Serial.write` returns short or 0 as soon as the small HWCDC transmit buffer is full, and USB drains it in milliseconds. `Console::say` used to give up after three zero-length writes in a row, which pass within microseconds, so every long answer (`read system.log`) was cut after a few hundred bytes and the tool waited for `CONFIG END` in vain; short answers mostly fit. Now `say` retries after a pause of 2 ms (`Delay`) and gives up only after 300 ms **without progress** (`kConsoleWriteStallMs`; every accepted byte starts the budget anew): a reading computer is never near it, a computer that stopped reading costs one loop pass a third of a second per write, not a hang. The rule that the firmware never waits for a computer that is not there still holds: `UartPort::hostConnected()` (`Esp32UsbPort`: `(bool)Serial`, the HWCDC connection state) is false with no computer on the port, and `say` then drops at once. A second fault sits in the framework: with the timeout at zero, `HWCDC::write` given more than its free room reports the whole chunk as written, drops the rest and marks the port as not connected (seen on the device the same day: a log answer cut after about 3.6 KB with the retry loop in place). `Esp32UsbPort::write` therefore offers only `Serial.availableForWrite()` bytes, so a short count is true. `device/main.cpp` also enlarges the transmit buffer to 4096 bytes before `Serial.begin` so most answers go out in one piece. Tests in `test_console`: a 32 KB answer through a port that takes 64 bytes and then stalls 20 calls arrives whole; with no computer nothing waits; a computer that stops reading makes `say` give up after the bound; progress resets the budget. Counter-check: the old three-stalls loop makes the first, third and fourth fail. Open: whether `(bool)Serial` is already true when the first command of a freshly opened port arrives (it is set from the USB interrupt once the host polls); if the first answer after opening is lost, that is where to look.

**The receive buffer (4.2.2).** The port's receive buffer was the default 256 bytes (only the transmit buffer was enlarged). The tools send a file in pieces of 64 bytes every 10 ms and the loop reads the port once in about 56 ms (open point 25), so about 350 bytes arrived between two reads and everything past the buffer was lost: `CONFIG WRITE` of a 626-byte file stored 512 bytes or got no answer, and a command line of 241 bytes got none (seen on the device on 2026-10-12). `Serial.setRxBufferSize(4096)` before `Serial.begin` holds a whole file and a whole command line (320 bytes at most) whatever the loop is doing. Verified on the device on 2026-10-13: `settings.toml` (615 bytes) was written with `deviceconfig.py write` and read back byte for byte.

## The loop's own line

Every half hour the system log gets one line from `board::LoopStats` (`src/board/LoopStats.h`, tests in `test/test_loop_stats/`), for example `Loop: longest pass 11320 ms, 32060 passes in 1800 s, asleep 1 %, sleep allowed in 0 % of the passes; per pass (ms) console 0.1, keys 1.2, modem 0.4, step 50.1, housekeeping 0.1, other 0.2`. A pass is the work of one turn of the loop, measured without the sleep or the pause that ends it; the longest one is what a key press could have waited for. "Asleep" is the part of the half hour spent in light sleep, and "sleep allowed" the share of passes in which the power policy let the processor sleep, which tells a policy that does not allow it from a sleep that does not happen. The last part is the average cost of a pass, by part: the card and the console, the keyboard and the touch chip, the modem and the haptic motor, the application's step with the drawing, the housekeeping (the battery check, the energy log, the requests to switch off and restart), and what is left over. They were added in 4.2.1 and extended in 4.2.2 to answer two questions with numbers (decisions D-20 and D-25): does anything block the loop for seconds, and why does the processor sleep 1 % of the time when the modem sleeps. Read on the device on 2026-10-14 (the night of 2026-10-13): nothing blocks, sleep is allowed in every pass, and the step costs 52 of 56 ms ([hardware-lessons.md](hardware-lessons.md)). Since 4.2.4 the line ends with the sleeps when there were any (decision D-33): `; sleep: 31990 times, ended by the timer 10, by a line 31980, other 0; low before sleep: keyboard 0, touch 0, ring 31980`. The processor wakes on the timer and on three lines (the keyboard's interrupt, the touch chip's, the modem's ring line, `device/Sleep.h`); a line that already has the level it is armed for ends the sleep at once. The line counts, for each sleep, what ended it and which lines read low before it. The night of 2026-10-14 named them: the keyboard's interrupt and the ring line read low before all 398,000 sleeps, none was ended by the timer or a line, and "asleep 23 %" was the going down and coming up of a sleep that never lasted, at 105 mA. Since 4.2.5 (decision D-34) the three lines have the processor's pull-ups, each is armed with the level it does not have at that moment, a sleep that nothing ended counts as no sleep, and the start logs the idle level of the three lines ("Wake lines: keyboard high, touch high, ring high", what the device prints with the pull-ups), on the cable too. The line shows the level a wake line idles at; a line that idles low would be armed to wake on high.

## The tools

`scripts/deviceconfig.py` (`list`, `read`, `write … [--restart]`, `battery`, `sms`, `restart`; `--help` lists them) and `scripts/webbridge.py` (a local web server on 127.0.0.1 that forwards every request through `CONFIG WEB`; the serial port is exclusive while it runs). Both need pyserial, which PlatformIO brings along: `~/.platformio/penv/bin/python scripts/deviceconfig.py list`. They are English, and `test_tools.py` runs them against a scripted console.

What the tools do with the console's answers, and what the tests pin:

- **`read`** prints the file byte for byte. The device announces the length and the 16-bit sum in `CONFIG CONTENT`, the tool reads exactly that many bytes (so blank lines and line ends are content, not skipped) and compares the sum; a read that one of the device's own log lines disturbed is repeated, three times at most. Of a long log the device sends the last 8 KB: the tool says on the error output where they begin. The device cannot tell a file that does not exist from an empty one, and the tool says that too.
- **`write`** announces the length and the sum, sends the bytes in pieces, and compares the length the device reports with the one it sent. `--restart` and `restart` wait for the device's `CONFIG OK restart`.
- **`sms`** prints the device's answer. `accepted` means the text left or waits for the network; `refused` (an empty text, one longer than the limit, a full queue of waiting texts) ends the tool with an error. A real line break in the text is refused by the tool: the console takes one line, a break is written `\n`.
- **`webbridge.py`** announces each request with `CONFIG WEB <n>`, sends it whole (at most 12300 bytes, the console's limit; a larger one gets a 413 from the bridge) and returns the response of the announced length. It forwards only the `Authorization`, `X-Phone-OS` and `Content-Type` headers and sets the length itself.
- **Commands of 3.2's tool that are gone:** `dial`, `hangup`, `query` and `motion` do not exist in 4.0's console.

## Not verified on the device

Everything: the start with real chips, the loop's timing, light sleep and its wake sources, the modem's goodbye on switch-off, the console over the real USB bridge (its reset behaviour included), and the bridge at full speed.
