# The generated pictures and the click-through demo

Decisions [D-48](../decisions.md), [D-49](../decisions.md), [D-53](../decisions.md). Code: `sim/Crawler.h`, the scene scripts `sim/demo/scenes*.txt` and the prelude `sim/demo/world.txt`, the page `sim/demo/page.html`, the generator `scripts/make_demo.py`; tests in `test/test_simulator/` (the walk), `test/test_demo_page/` (the page) and the generator's own checks. Nothing generated is committed: `out/` is ignored, and CI uploads `out/demo` as the artifact `demo`. The pictures are made by running the simulator ([simulator.md](../simulator.md)), never by hand.

## Building it

```sh
pio run -e sim
python3 scripts/make_demo.py        # about 4 minutes on eight processors; writes out/demo/ and prints what it made
```

Open `out/demo/index.html` in a browser. The pages of the user guide may refer to the pictures by the artifact's name but must not need them to be read.

## The walk

`program --crawl <dir>` finds every picture the keys and a finger can reach, breadth first. The device has no way to save and restore its state, so each step starts a new simulator on the card, plays the prelude (`sim/demo/world.txt`: two texts and a missed call, so that the lists have something in them), replays the steps of the path (`key up`, `tap 120 160`, `advance 7s`: console lines) and looks at the panel. From every state the seven keys are pressed, and then the device is started once more to ask the visible screen where a tap does something (`Screen::touchTargets()`, [ui-framework.md](../ui/ui-framework.md)): the soft keys, the tiles, the rows, the buttons; the middle of each is tapped. A state is a picture on a screen in a language; the graph (`graph.json`) has the states, the screen, the language and the soft keys of each, the keys that were pressed and changed nothing (`idle`), and an edge for every key (`"key"`), every tap (`"tap"`: the rectangle a finger hits, in pixels of the panel) and every wait (`"wait"`: seconds) that leads somewhere else. The simulator's own reason is reported when a device cannot start at all (a work directory that is not the simulator's: `Crawler::error()`, `test_simulator`).

**The language is part of the state.** The Language page puts its cursor on the language in use, so the same keys pick different rows in different languages, and a choice leads into the interface of the chosen language. A walk found in English and replayed in German and French (as the first demo was, D-48) therefore chose German where it meant English, left 30 edges in German and 14 in French that led to the picture they started from, and showed a French picture after the English row had been tapped (D-53). The walk is now one graph over all three: it is started once in each language (`--languages en,de,fr`, the starts are `starts` in the graph), a choice on the Language page leads on to the states of the chosen language, and each state's picture is taken in the language it is in (`<language>/n<state>.png`, the folder is the state's `lang`, not the language the device was started in). Each language's page begins at its own start. The language of a start is chosen as the device chooses it (`AppCore::setInterfaceLanguage`, which the card keeps), so a restart keeps it. The pseudo-language of the simulator ([simulator.md](../simulator.md)) is not on the device and not in the walk: the walk runs without it (`--no-pseudo`, always, in `--crawl`), and the Language page lists English, Deutsch and Français and nothing else.

**Nothing is cut off.** Every key and every tap of every state is followed, so that a key which is drawn leads where the device would lead. The earlier walk kept at most 30 states per screen (`--per-screen`) and recorded no edge to the others: about 170 pairs of a state and a key were dead although the key was drawn (the Back, Home and Inbox keys on the language page, on the settings pages, on the pages of the messages and of the recipient; Back on the SOS page, which could then not be left). The walk now ends where the graph ends. Two fuses stop a run that does not: `--depth` (30 steps in a path) and `--max-states` (20,000), and a walk that reaches one is not complete and fails (exit status 1; `Crawl::complete`). A step that leads to the picture it started from is no edge and is noted in the state as `idle`: a key at the end of a list, the choice of the language in use (the device does nothing there either: `AppCore::setInterfaceLanguage` with the language in use), Reset on the motion page with the sensor at rest.

**What it presses.** Everything, since D-53; the earlier walk pressed no key during a call and did not choose a ready-made message because those change the world and not only the picture. Hang up is the Back key and the bar at the foot of the call page, and it ends the call as it does on the device (the walk reaches the call page by dialling; the "No call" page follows, and Back leaves it). The device answers no other key during ringing and a call, and the walk records that. A ready-made message is sent by Enter and by a tap on its row; the device is on the home screen after it, the walk too, and the picture is the home screen's, so the edge leads to the home state: the sent message itself is not carried into the lists of the states that follow, because the walk keeps no history (a walk that did would multiply every list by every message that could have been sent). The page shows the world as it was at the start, which the scenes also do. A screen that ends by itself, the key test of the self-test page ("Ends in 6 s without input"), gets one more kind of edge: on the states of that screen the walk lets seven seconds pass (`Crawler::kWaitSeconds`, `endsByItself`), and where the picture changes the edge is a `wait`, which the page follows when the time has passed, as the device does.

**Size.** On this tree (a run of `make_demo.py`, whose last line says the same) the walk has 4,608 states, 1,536 in each language, with 68,739 edges (keys, taps and waits), 5,358 steps that changed nothing, and its deepest state is 16 steps from a start. That is 4,653 pictures, 44 MiB of PNG files, a `graph.json` of 3.7 MiB and the demo's `index.html` of 4.5 MiB with the graph in it; `out/site/` with the web page is 53 MiB. Most of the states are the combinations the screens have: the self-test page (1,662 states: its cursor, the pattern played last, the light), the settings pages (1,260) and the compose page (540). One walk takes about 14 minutes on one processor and 4 on eight (`--jobs`, default the number of processors, at most eight: each replay is a simulator of its own on a card of its own, the results are put into the graph in the order of the steps, so the graph and the pictures are the same whatever the number; CI has fewer processors). The limit to stop and ask about was 5,000 states per language or 200 MB.

## The scenes

The pictures the keys do not lead to need something to happen: a call coming in, school time, a flat battery. `sim/demo/scenes.txt` (the child's device) and the other `scenes*.txt` files (each with a `# data:` line for its card) are scripts that set the world up and call `shot <name>`; the generator runs each once per language, after switching to it.

## The page

`index.html` is one file: the graph, the scene names and the words are embedded, the pictures are beside it (`<language>/n<state>.png`, `<language>/scene-<name>.png`). It shows the picture, the seven keys (enabled where the key leads somewhere), "start over", and the list of scenes. The language selector is another device started in that language: it swaps every word and goes to the start state of that language, because the pictures of a state are in the language the device is in there, which only the Language page changes (so a picture can be in a language other than the words of the page, as on a device that was set to another language than the parents' phone). A click on the picture is a tap: when it falls in the rectangle of a tap edge of the state, the page follows that edge, and the picture shows a pointer while the state has one. A state with a `wait` edge is left when its time has passed, and any move before that starts the time again. The language is the address's (`?lang=de`, which the link from the web page carries, English too), else the browser's, else English. Pictures are drawn without smoothing.

**The page has no words of its own.** Its title, keys, status line and scene names are the `demo.*` keys of the host-only files `tools/lang/demo.<code>.toml` in English, German and French (they are not shipped to the device, so they do not weigh on the limit of a catalog on the card, [i18n.md](../core/i18n.md)), and `test/test_demo_page` fails when the markup holds text or the script holds a sentence. A new scene needs a script line, a `demo.scene-<name>` key in every `tools/lang/demo.<code>.toml` and a row in `SCENE_WORDS` of the generator.

## What the generator checks

`scripts/make_demo.py` exits with 1 when: a word of the page or the name of a scene is missing in a catalog; a scene has no name or a name has no scene; a picture of a state or a scene is missing; the walk has fewer than 60 states; the number of pictures is not the number of states plus the scenes in every language; or the graph breaks a rule of `check_graph`, which `test/test_make_demo/test_graph.py` pins on small graphs (each rule fails when it is broken):

- the walk is complete (no state was left at a limit), and each language has a start state that is in that language;
- no state is in a language the device does not have (the pseudo-language);
- every key of every state was pressed: it has an edge or is noted as unchanged;
- a soft key that is drawn is not dead: it has an edge, except the arrows of a list (at the end of a list the device does nothing either), the choice of the language in use on the Language page and Reset on the motion page, which are named in `SOFT_KEY_IDLE_OK` with the reason;
- every state can get back to a home screen by following edges;
- no edge changes the language except one from the Language page (the restart on the Radio page keeps it);
- on the Language page of each language, each other language can be chosen with a key and with a tap;
- the walk reaches, in every language, the screens the keys lead to on the child's card (home, lock, clock, phone, call, messages, compose, recipient, SOS, options, network, language, GPS, radio, motion, self-test, power).

CI therefore fails when a screen stops being reachable, a key that is drawn stops leading anywhere (a cap, a limit, a state that cannot be left) or a translation is missing.

The number-typing page, the Wi-Fi page and the status page are not in the walk: they open only on a device that may write to anybody or has the parents' tools, and the child's card has neither. `sim/demo/scenes-parent.txt` (on `sim/data-parent`) takes them as scenes, in every language: the Wi-Fi page off and with the access point, the status page, and the number page. The numbers of a run are printed by the generator (`make_demo: <pictures> pictures, <states> states, <scenes> scenes, <languages> languages`); a run on this tree prints 4,645 pictures, 4,600 states in 3 languages, 68,699 edges, 15 scenes.
