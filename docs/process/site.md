# The web page

Code: `site/index.html` (the page), `tools/lang/site.<code>.toml` (its words), `scripts/make_site.py` (the assembly), `scripts/build_wasm.sh` and `sim/wasm_main.cpp` (the simulator for the browser), `.github/workflows/pages.yml` (the build and the publication on GitHub Pages); tests in `test/test_make_site/` (the assembly) and `test/test_site_page/` (the page). Decisions [D-48](../decisions.md) and [D-58](../decisions.md).

The page presents the project to somebody who has not seen the device: how it gets onto a device (the one board it has been built and tested on so far, the code, the card, the flash command, with no connection to the board's maker), the three words the project keeps apart, how the code is layered, what the child's phone does and refuses, and where to read on. Its first screen is the device itself, as the click-through demo of [demo.md](demo.md) shows it: the pictures the simulator drew from the firmware's own code, the three keys under the screen and the four keys of the keyboard that lead from one picture to the next, the touch targets of each picture laid over it as invisible buttons where the screen says a finger hits something (a tile, a row, a soft key), and the language selector that opens the same page in another language. The arrow keys, Enter and Backspace work when the device has the focus, and it keeps it: after a click on a touch target (which the next picture replaces) or on a key that the move disables, the page gives the focus back to the device, so that the arrows go on driving it instead of scrolling the page (D-53). The scenes the keys do not lead to (a call coming in, school time, a flat battery) are linked, not repeated: the full demo page is published beside it under `demo/`.

**What the page shows is not the simulator running.** The simulator ran on the build machine and took a picture of every state the keys and a finger reach; the page walks through those pictures along the graph of the walk. The graph is one over the three languages ([demo.md](demo.md)): a state is a picture in a language, each language's page begins at the state its device starts in, the Language screen leads from one language into another and the pictures that follow are in the language chosen, whatever the words of the page say. A screen that ends by itself, the self-test's key test, goes on after its time on the page too. Nothing on the page is drawn by hand, and nothing generated is committed: the workflow builds the simulator, runs `scripts/make_demo.py`, assembles `out/site/` and publishes it, so the page always shows the pictures of the commit it was built from.

**The part "Try it live" is the simulator running** (D-58). Below the first screen, a button starts the simulator itself, the C++ of the firmware's core, screens and card compiled to WebAssembly ([simulator.md](../simulator.md)): the panel is drawn on a canvas, the seven keys are buttons and the keyboard (arrows, Enter, Backspace, Escape for Back, F1 to F3 for the keys under the screen, typed characters as text), a click on the screen is a touch, and no console is shown. Buttons make situations happen through the simulator's own commands, on the card `sim/data` (the child's phone, invented numbers): a text from a parent (`sms` from Parent One, its sentence a catalog word in the page's language), a call from a parent (Enter answers, Back hangs up), the battery almost empty and charged again, no network and the network back, and the SOS (the tile on the home screen). The simulator starts in the language of the page. It is loaded only when the visitor presses the button (about 0.4 MB over the wire), so the first screen stays light, and the page says that it runs on fakes: the clock, the e-paper panel, the radios and the position are the simulator's, not the device's. The parents' page is not part of it: a browser page cannot listen on a socket. Nothing generated is committed: the workflow installs Emscripten, builds the simulator with `scripts/build_wasm.sh` and `make_site.py` puts it under `live/`.

## Building it

```sh
pio run -e sim
python3 scripts/make_demo.py        # out/demo/
scripts/build_wasm.sh               # out/wasm/, the simulator for the browser (needs Emscripten: brew install emscripten)
python3 scripts/make_site.py        # site/ + out/demo/ + out/wasm/ + VERSION -> out/site/ (--no-live: without the simulator)
python3 -m http.server -d out/site 8000   # then open http://localhost:8000/ (English) and http://localhost:8000/de/
```

`make_site.py` copies `site/` to `out/site/`, the demo to `out/site/demo/`, the simulator for the browser to `out/site/live/` (`--no-live` leaves it out; the button then says that it cannot load it) and `VERSION` to `out/site/version.txt`, which the page reads for its version number. It renders the page once per language: `out/site/index.html` in English, the default, and `out/site/<code>/index.html` for each other catalog (`de/`, `fr/`). Each page has its language's words written into its markup, its `<html lang>` and its data-root (`../` in a language's folder, so that its pictures and the demo are found), the words of that language only embedded for the selector, and the head links: a `canonical` link, an `hreflang` link to every language's page and `x-default` for the English one. The `--url` argument is the address those links are made for (default `https://paulwilke.github.io/Phone-OS/`). It exits with 1 when the demo or the simulator for the browser is missing, when the demo's graph has no start state for a language (a graph of an older walk: the pictures of the first screen and the preview image are those of the state a language starts in), when a language lacks a word the page uses (the key is named), when the page lacks one of its markers, or when a file the page fetches at run time is not in the result, so a run that "built" a page without its pictures or its words fails; `test/test_make_site/test_site.py` checks these cases on small trees.

## Its words and its language

The page has no words of its own, as the demo page has none ([demo.md](demo.md)): they are the `site.*` keys of the host-only catalogs `tools/lang/site.en.toml`, `site.de.toml` and `site.fr.toml`, which the device never gets. An element that says something is empty in `site/index.html` and names its key: `data-i18n="site.hero.title"` for its text, `data-i18n-alt`, `data-i18n-aria-label` or `data-i18n-content` for an attribute. The script names the rest by key (the labels of the keys, the names of the screens in the status line, the touch targets' labels). `scripts/check_i18n.py` checks the set like the others, and `--usage` reads `site/` for the keys the page uses. The German and French words use the terms of the user's guides ([benutzerhandbuch.md](../de/benutzerhandbuch.md), [guide-utilisateur.md](../fr/guide-utilisateur.md)) and address the reader the same way; numbers are written by the script the way of the language in use (2,500 / 2.500 / 2 500).

**The language is the path, never the browser's.** The English page is at the root of the address (`/`), the German one at `/de/` and the French one at `/fr/`. Each is a page of its own, prerendered with its words, so a reader without a script, a link preview and a search engine see the page in the language of its address; no page reads the browser's language, and none rewrites the address. The selector goes to the page of the chosen language, at the same place in the page (its hash kept). Links shared before the pages were split name the language in a query: `?lang=de` on the root page is sent to `/de/` by the page's script, because such links are already out there; a code the page does not have is ignored. Every page names its own canonical address and an `hreflang` link to each language's page, with `x-default` for the English one; these addresses are made from `--url` (the default is the GitHub Pages address, and the workflow passes nothing), so a custom domain changes that default and nothing else. The user's guide button leads to the guide in the language of the page; the other documents are English. The link to the full demo under `demo/` carries the language of the page in every page, the English one too: `?lang=en` from the root, and `?lang=de` from `/de/`, where the link is `../demo/index.html?lang=de` (one folder up). Without it the demo would follow the browser's language, and a German reader of the English page would land in a German demo (D-53). The demo itself reads `?lang=` before the browser's ([demo.md](demo.md)).

`test/test_site_page/test.mjs` (Node, no dependencies) also runs the script of the live part against the same kind of fake: nothing is loaded before the button, the button loads the loader from `live/` once (one folder up on a language's page), the simulator is started in the page's language with its output going nowhere, every situation sends the commands above, and a simulator that does not load says so and can be asked again. It fails when the markup holds text (only a repository path in `<code>` is allowed), when an attribute or the description holds words, when the script holds a sentence, asks the browser for its language or rewrites the address, and runs the script against a small fake of the DOM: the root page stays English whatever the browser says, `?lang=de` on it goes to `de/`, the selector goes to the other language's page with the hash kept, the pictures, the status line, the labels of the keys, the touch targets and the link to the full demo are in the language of the page the fake was given, a state reached through the Language screen shows the pictures of its own language, the device keeps the focus after a tap and after a key that the move disables, and the self-test's key test goes on after its seven seconds.

## Rules the page keeps

- **English at the root, German and French in their own folders**; the words are in `tools/lang/site.<code>.toml`, none in the page. The demo page under `demo/` keeps its rule of having no words of its own ([demo.md](demo.md)).
- **No personal data**: the pictures show the invented card of the simulator (the child Alex, Parent One and Parent Two).
- **No pictures of its own**: a picture on the page is a picture of the demo, by its path, so a screen that changes in the code changes on the page at the next build.
- **Three words kept apart**: the page says that its pictures are the simulator's, and claims nothing about the device that the decision log does not.

## Publishing

The workflow installs Emscripten (the `emsdk` of a pinned version) next to PlatformIO. It runs on every push to `main` and on request (`workflow_dispatch`). GitHub Pages must be set to build from GitHub Actions once, in the repository's settings; that setting is the owner's. The address is `https://paulwilke.github.io/Phone-OS/`, the default of `--url`; a custom domain needs that default changed in `scripts/make_site.py`, since the workflow passes no `--url`.
