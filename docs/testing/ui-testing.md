# Automated testing of the interface

A concept, not a description of code: it says how the screens of Phone OS are tested automatically, what of it exists today and what a UI testing framework has to add. The framework itself is built in a repository of its own against [ui-testing-framework-requirements.md](ui-testing-framework-requirements.md) and used here through one configuration file, [ui-tests/ui-tests.toml](../../ui-tests/ui-tests.toml). Until that framework exists the configuration is not run by anything; open point 47 in [open-points.md](../open-points.md) waits for the framework repository. The eight choices that shape the framework were the owner's and are decided in [D-57](../decisions.md) (the section "Decisions" below).

## What the interface is

Everything a child or a parent sees of Phone OS is one of five things, and each is tested in its own way today:

| Interface | Drawn by | Tested today by |
|---|---|---|
| the e-ink screens of the device, 240 × 320 pixels, one bit per pixel ([ui-display.md](../ui/ui-display.md)) | the firmware's screens in `src/ui/screens/` on a `ui::Display` | widget and screen tests on the host (`test/test_widgets/`, `test/test_screen_lock/` and one directory per screen), with golden pictures of regions under `test/golden/` and clipping asserted in every language ([ui-layout-testing.md](../ui/ui-layout-testing.md)) |
| the same screens through the whole wiring, with the refresh policy of the panel ([simulated-panel.md](../process/simulated-panel.md)) | the simulator, `pio run -e sim` ([simulator.md](../simulator.md)) | the scripted scenarios in `sim/scripts/*.txt`, run headless by CI, with text assertions and five full-screen golden pictures under `sim/golden/` |
| the click-through demo: a picture of every reachable state in every language | `scripts/make_demo.py`, which has the simulator walk the interface by its keys | `test/test_demo_page/test.mjs` (the page's behaviour on a fake DOM) and `test/test_make_demo/test_graph.py` (the rules of the walk) |
| the parents' web page, served by the device | `web/index.html`, generated by `scripts/gen_web.py` | `test/test_web_page/test.mjs`, `test/test_sim_web/` through the real socket of the simulator |
| the public site ([site.md](../process/site.md)) | `scripts/make_site.py` | `test/test_make_site/test_site.py`, `test/test_site_page/test.mjs` |

This concept is about the first two rows: the screens of the device. The three HTML pages keep their Node and Python tests, which already check what matters about them (no words of their own, every key in every catalog, the language selector); a frame-comparing framework would add nothing there and is kept out of scope.

## What a UI test is here

A UI test is a **scenario**: a list of steps that drive the device, with **expectations** between them.

- **Steps** are what the world and the child do: key presses (`key down down select`), typed text (`type`), touches (`tap 200 80`), time passing (`advance 40s`), and events injected below the capability interfaces: a text arriving (`sms`), a call (`call`, `remote hangup`), the battery and the charger (`battery 20`, `plug charging`), the network and the SIM (`network none`, `simcard pin`), the receiver (`gps fix`), the motion sensor, Wi-Fi, a request to the parents' page (`web post`). These are the console commands of the simulator ([simulator.md](../simulator.md), "Console commands").
- **Expectations** are of three kinds, from cheap to strict:
  1. **Screen text.** `see <catalog key> [name=value]` asserts that the screen says the catalog's text for that key, in the language of the moment; `say <text>` asserts a literal (a contact's name). The match is a whole word in one of the four fonts at any place of the screen, so a word that is cut off or covered is not found. This is the assertion that makes a scenario valid in every language without a picture per language.
  2. **State.** `check screen sos`, `check unread 1`, `check sms-sent 1`, `check settings-has language = "de"`: what the device believes, read from the runtime. A state check tells a failing picture apart from a failing behaviour.
  3. **A frame.** `golden <name>` compares the picture the panel shows (after the refresh policy, so a frame that cost no refresh is not shown) with a stored picture, pixel for pixel. This is the only assertion that catches a layout that moved, a font that changed or a line that is one pixel too low.

A region assertion, a tolerance and a picture per language are the parts the simulator does not have yet (below).

**Tolerances.** The panel has two colours and the rendering is deterministic, so the default comparison of a frame is exact: one pixel is a failure, as `testing/Golden.h` already does. A tolerance is the exception, named in the configuration per scenario or per region, for the two things that are legitimately unstable: a region that shows a value nobody fixed (the clock of the status bar when a scenario does not set the date) is **masked**, and a region whose anti-aliasing-free text may shift by a known amount is given a **pixel budget**. A tolerance on the whole frame is not offered: it would hide the one-pixel regressions the frame comparison is for.

## The layer the tests drive

The tests drive the **simulator's script interface** and nothing below it. The simulator runs the same application core, screen stack, configuration loader and web service as the firmware, on scriptable fakes of every capability ([test-doubles.md](../process/test-doubles.md)), so a scenario exercises the real screens, the real refresh policy and the real wiring, and a failure is a failure of the product's code, not of a test double. Time is a counter the script moves, so a run is deterministic and a second costs no time.

The framework starts the binary (`pio run -e sim` builds it; CI builds it headless on a plain Linux runner) and talks to it over its console: either a whole scenario file with `--script`, which is what CI does today, or line by line over standard input and output in `--interactive --headless` mode, which is what a framework needs to attach a report to each step. A **device build is out of scope**: the firmware's screens are only reachable over USB on a flashed device, the device has no frame dump and no injected events, and flashing is the owner's decision ([CONTRIBUTING.md](../../CONTRIBUTING.md)). The requirements leave a door open for a device adapter later, as a second target of the same scenario format.

### What `sim/scripts` can already do

The scenario language of the simulator already is most of a UI test language:

- 24 scenarios under `sim/scripts/`, each a story with a comment that says what it pins, run by CI and by `test/test_simulator/` on every change; `scripts/counter_check_scenarios.py` proves each can fail by breaking the behaviour it is about.
- Every input of the device: the seven keys, typed UTF-8 text, a touch at a pixel.
- Every event of the world the device reacts to, injected through the capability fakes: text and call, radio, battery and charger, signal, network and SIM, the receiver, the motion sensor, Wi-Fi, the parents' page over the real socket, the clock (`date`) and time passing (`advance`).
- Text assertions by catalog key, so one scenario is valid in every language, and literal text assertions.
- State assertions on the screen stack, the lock, the call and SOS state machines, the counters of texts sent and vibrations played, the log, the card and the web page's answers.
- A full-screen golden picture, in the ASCII format of `testing/Golden.h` (`#` black, `.` white, one line per row), written with `UPDATE_GOLDEN=1` and reviewed in the diff of a pull request; a mismatch prints the first six differing rows.
- The panel as a PNG (`screenshot`, `shot`), as ASCII (`ascii`), and a walk of every reachable state with a picture per state and language (`--crawl`, used by the demo).
- A card per scenario (`# data: <dir>` in its head), the pseudo-language for hostile layouts, and the languages a walk starts in.

### What is missing

What a framework has to add, in the order a first version needs it:

1. **A result per step.** The console prints `error: ...` when a command fails and the run exits with status 1 at the end; a report needs to know which line failed. The owner chose one result line per command (`ok` or `error: ...`) as the protocol ([D-57](../decisions.md)); until the simulator prints it, a framework gets by with `echo <token>` after every command and reads up to the token.
2. **A frame dump on the wire.** `ascii <file>` and `screenshot <file.png>` write files; a framework that drives the console over standard input can read the file after the token arrives. A dump on standard output between known markers would save the file round trip.
3. **A golden picture per language.** `golden smoke-home` compares one file whatever the language; `smoke.txt` works around it with a name per language (`smoke-home-de`). The framework names golden files by scenario, step and language.
4. **A region.** `golden` compares the whole 240 × 320 panel; a region assertion (the content area without the status bar's clock) and a mask do not exist on the console, although `golden::expect` takes a rectangle in the host tests.
5. **A diff image.** A failing `golden` prints rows of `#` and `.`; a reviewer wants expected, actual and their difference as pictures next to each other.
6. **A report.** Nothing writes JUnit or a summary a pull request can show; CI's loop over `sim/scripts/*.txt` stops at the first failing scenario.
7. **Parameters per language and per card.** A scenario runs in the language of its card; starting the same scenario in each of the three languages is the framework's loop, as `--crawl --languages` does for the walk.
8. **A tolerance.** The comparison is exact and has no mask.

Items 1, 2 and 4 are small additions to `sim/Simulator.h` and belong to this repository, as their own bounded problem once the framework's protocol is fixed; a first version of the framework can do without them, and the others are the framework's.

## Golden frames

A **golden frame** is the picture of the panel at one step of one scenario in one language, approved by a person and stored in the repository.

- **Format.** The format in use today is the ASCII art of `testing/Golden.h`: one character per pixel, `#` black, `.` white, one line per row, 77,120 bytes for a full screen. It is readable in a diff, needs no tool, and is what `sim/golden/` and `test/golden/` hold already. The framework reads and writes it, so the five pictures of `sim/golden/` are the first golden frames of the suite. The owner chose it over a binary PBM (one bit per pixel, 9,600 bytes a frame, but a renderer is needed to review it) in [D-57](../decisions.md); the format is one setting of the configuration, so a move is possible later.
- **Where.** Under one directory of this repository, by language and name: `ui-tests/golden/<language>/<scenario>.<step>.txt`. A PNG of each is **not** committed; the framework renders it on demand for a reviewer and CI uploads the rendered pictures as an artifact.
- **Review.** A changed golden frame is a changed file in the pull request, like code. The author of the pull request approves it with one sentence in the description that says why the picture changed ([D-57](../decisions.md)); the reviewer looks at the rendered before, after and difference the framework attaches to the run. A golden frame that changes without that sentence is a finding of the review.
- **Update.** `UPDATE_GOLDEN=1` writes every compared frame today; the framework takes an approve command that writes only the frames of the scenarios named, prints what it changed, and never creates a frame silently in CI: a missing frame fails there and says how to create it, as `golden::expect` does.
- **Language coverage.** A golden frame is kept in English for every scenario step that has one, and in German and French where a layout is known to be tight (a tile, a soft key, a title); the text assertions cover the words in all three languages, and the host tests cover clipping in the pseudo-language ([ui-layout-testing.md](../ui/ui-layout-testing.md)). Keeping every frame in every language would triple the files for little information ([D-57](../decisions.md)); the configuration says per scenario which languages have pictures.

## How a test fails usefully

A failing step reports, in this order, what a person needs to decide whether the product or the test is wrong:

1. the scenario, the language, the card and the line of the failing step, with the step's text;
2. for a text assertion: the key and the words that were expected in that language, and the picture of the screen as it was, so a person sees what it says instead;
3. for a state assertion: expected and actual value;
4. for a frame: the first differing rows as text, the count of differing pixels, and three pictures as files: expected, actual and their difference (differing pixels black on white), named after the scenario, step and language, so a reviewer opens them from the CI artifact;
5. the last twenty lines of the device's log and the `state` summary, because a wrong picture is usually a wrong state a few seconds earlier;
6. the commands to reproduce it on a laptop: the one line that runs this scenario alone.

A scenario stops at its first failing step (the steps after it would fail for the same reason); the suite does not stop and runs every other scenario, so one pull request shows all of what it broke.

## How it runs

**In CI**, as one step of `.github/workflows/ci.yml` after "Simulator build", in place of the shell loop over `sim/scripts/*.txt` once the framework runs every scenario there ([D-57](../decisions.md)): the framework is installed at a pinned version from its repository, reads `ui-tests/ui-tests.toml`, runs every scenario in every configured language, writes a JUnit file that the workflow publishes, uploads the diff pictures as an artifact when something failed, and exits with a status the workflow understands. The whole suite stays under five minutes on the runner: the simulator advances time without waiting, and a scenario takes seconds. The counter-check (`scripts/counter_check_scenarios.py`) stays outside CI, as today, because it rebuilds the simulator.

**Locally**, one command from the repository root runs the suite or one scenario, in one language or all, and prints the same report to the terminal; a second command approves changed frames. The simulator's own ways stay: a scenario file still runs with `--script`, and the window build (`pio run -e sim-sdl`) still lets a person watch a scenario.

**On every change** means every pull request and every push to `main`, like the other checks. A scenario that is flaky is a bug: time is deterministic, so a scenario that passes once and fails once has found an order dependence in the product or a value the test did not fix.

## Translations and the three languages

The device ships English, German and French, and a user catalog may add a fourth ([translating.md](../translating.md)). The suite covers them like this:

- Every scenario runs in English, German and French unless its configuration says otherwise (a scenario that drives the Language page itself runs from one start language). The start language is set as the Language page sets it, so the card keeps it and a restart in the scenario brings the device back in it.
- Text assertions use catalog keys, so the same scenario checks the German and the French words without a German or French copy of the scenario; a scenario that asserts a literal English word (`say Settings`) is marked as English only or rewritten with its key.
- Golden frames are kept per language where the configuration says so (above).
- The pseudo-language stays in the host tests, where every widget is drawn in it with clipping asserted, until the suite stands ([D-57](../decisions.md)); after that the suite may run a scenario in `qps-ploc` as a smoke test of the layout under hostile words, with text assertions only and no frames.
- A user catalog is covered by the scenarios that exist for it (`user-catalog`, `bad-catalog`), which run from cards under `test/data/`.

## Out of scope

- **The real device.** No test here flashes, drives or reads the T-Deck. What the simulator cannot prove ([simulator.md](../simulator.md), "What the simulator cannot prove") stays unproven by these tests: timing, the true look of the e-ink panel (ghosting, temperature), power and sleep, the real loop. The owner's acceptance test on the device ([de/abnahmetest.md](../de/abnahmetest.md)) covers that.
- **The modem, the receiver and the radio.** Their answers are scripted by the fakes; a real operator, a real SIM and a real sky are not here. The AT layer has its own host tests and fuzzers.
- **The three HTML pages** (demo, parents' page, site): their Node and Python tests stay as they are.
- **Behaviour without a screen**: the logic modules have their host tests (`pio test -e native`), and [app-behaviour.md](../app-behaviour.md) is their inventory; a UI test does not replace a unit test, it checks that the pieces are wired together in front of the child.
- **Performance of the device**: frame budgets are measured by `test/test_frame_budget/` on the host, not by scenarios.

## Decisions

The owner decided the eight choices that shape the framework on 2026-10-31; the entry [D-57](../decisions.md) holds the options and the reasons. Settled:

1. **Golden format.** The ASCII art of `testing/Golden.h`, as `sim/golden/` and `test/golden/` hold it today; the format is one setting of the configuration (R-57).
2. **Which languages get pictures.** English for every frame, German and French where a layout is tight, named per scenario in the configuration (R-53).
3. **Replacing the CI loop.** The framework replaces the shell loop over `sim/scripts/*.txt` in CI once it runs every scenario there; until then the loop stays.
4. **Where the golden frames live.** `ui-tests/golden/`, next to the configuration, so the suite is one directory (R-43).
5. **Language of the framework.** Python 3.12 with the standard library (R-67, R-70).
6. **The protocol.** Standard input and output with one result line per command, `ok` or `error: ...` (R-19, R-20); the simulator's result line is a bounded change of this repository that comes with the framework's first use.
7. **The pseudo-language.** It stays with the host tests until the suite stands.
8. **Who approves a golden frame.** The author of the pull request, with one sentence in its description that says why the picture changed.

What is still open is the framework itself: open point 47 waits for its repository.
