# Translations

The interface can be shown in several languages. English, German and French ship with the firmware; further languages are added by writing a catalog file, with no change to the code.

All translatable text lives in **catalogs**, **two TOML files per language**: `lang/<code>.toml` for the device (its screens, notices, SMS bodies, system entries) and `lang/web/<code>.toml` for the parents' web page and the configuration form (`web.*`, `config.*`). English (`lang/en.toml`, `lang/web/en.toml`) is the *reference* of its set: every other catalog is checked against it, and it is the language used when a message is missing from the selected one. A key is in one set only.

The `Translator` loads the **device set at start**; everything on the device asks for it. The **web set** is held apart: it is read when the web service first needs it (`GET /api/lang/<code>`, through `Translator::ensureWeb()` and the sources the host gave it: the shipped files, then the card's `/lang/web/`) and let go when the page is no longer reachable (Wi-Fi off: `releaseWeb()`). A language that has a device catalog and no web catalog is English on the page, exactly as a missing key is.

## Catalog format

```toml
[meta]
code   = "fr"                 # language tag, e.g. "fr" or "pt-BR"; equals the file name
name   = "French"             # English name of the language
native = "Français"           # the language's own name, shown in the language picker
plural = "zero-one-other"     # plural rule, see below

[strings]
home.phone      = "Téléphone"
call.busy       = "{name} : occupé"
messages.unread = ["{n} nouveau message", "{n} nouveaux messages"]
```

- **Keys** are lowercase words, digits, `.`, `_` and `-`. The dotted key is the whole key; the parser does not build nested tables.
- **Values** are double-quoted strings with the escapes `\"`, `\\`, `\n`, `\t` and `\uXXXX`, or — for a message with a count — an array with one string per plural form.
- **Placeholders** are written `{name}`. Literal braces are written `{{` and `}}`. A translator may put a placeholder anywhere in the sentence, because word order differs between languages.
- **Comments** start with `#`.

The parser is strict: any problem (an unknown section, a duplicate key, a string that is not closed, a wrong number of plural forms, a missing header field) is reported with its line number and the catalog is rejected as a whole. A half-loaded catalog would show raw keys or English on the child's screen weeks later.

## Plural rules

| Rule | Form 0 | Form 1 | Languages |
|---|---|---|---|
| `single` | every count | — | languages without plural |
| `one-other` | exactly 1 | everything else | English, German, Spanish, Italian, Dutch |
| `zero-one-other` | 0 and 1 | everything else | French, Portuguese |

A message with a count has one form per category of its rule (the number of forms is checked). A message with a single form serves every count.

## Lookup and fallback

`Translator` looks a message up in the selected language, then in English. A key found in neither is returned as the key itself and remembered in `missingKeys()`, so a missing message is plainly visible (`home.phone`) instead of silently empty. `fallbackCount()` counts the lookups that had to fall back to English; tests assert it stays zero for the shipped languages.

A regional tag falls back to its language: selecting `fr-CA` uses `fr` when no `fr-CA` catalog exists.

### A message in another language

The language of the reader is not always the language of the screen: an SMS to a parent goes out in the parents' language whatever the child's screen shows. `getIn(code, key, args)` and `pluralIn(code, key, n, args)` are `get()` and `plural()` in the language named by `code` — the regional tag falls back to its language, an unknown code gives English, a key missing in that language falls back to English (and is counted in `fallbackCount()`). The selected language is not touched.

`textsInAllLanguages(key)` returns the text of a key in every language that has it, without repeats, in the order of the language codes. The trigger words of the remote query come from here (`sms.command.where`): a parent may write the word in any language the device speaks, and a language added later adds its word without a change in the code. Asking is not a lookup: a key that no language has gives an empty list and is not remembered in `missingKeys()`.

## Formatting

`format()` (`src/i18n/Format.h`) knows only `{name}` placeholders: no width, no precision, no conversions. A message therefore cannot crash the device with a wrong specifier, and a missing or misspelled placeholder is found by a check instead of printing garbage. A placeholder without a matching argument is left as written and counted.

## User catalogs

`Translator::addUser()` takes the text of a catalog from outside the firmware:

- A catalog with a **new code** adds a language to the picker.
- A catalog with the code of a **shipped language** overrides single messages of it; the rest stays as shipped.
- It is rejected — nothing is added — when it has a syntax error, or when a message uses different `{placeholders}` than the English one. Missing messages are fine: they fall back to English.

`Translator::addUserWeb()` does the same for the page's set (`/lang/web/<code>.toml` on the card): the same checks, the placeholders compared with `lang/web/en.toml`. A user catalog for the page changes the page's words and never the device's, and a code that only the page has does not appear in the device's picker.

To write a translation: copy `lang/en.toml`, change `[meta]`, translate the values, keep every `{placeholder}`; then, for the page, the same with `lang/web/en.toml` ([translating.md](../translating.md)). Each can be done alone.

### What is shipped, what is host-only, and the limit

- `lang/<code>.toml` are the device's catalogs **shipped to the device**: English (the reference), German, French. `lang/web/<code>.toml` are the page's, in the same three languages (embedded like the others; read on demand).
- `tools/lang/<set>.<code>.toml` hold words that only a tool on the computer shows and that the device never gets: today the sets `demo` (the click-through demo page, [demo.md](../process/demo.md)) and `site` (the project's web page, [site.md](../process/site.md)). The simulator and the demo generator read both and merge a host set into the language of the same code. A key is in one place only.
- **A catalog on the card is read only up to `ConfigLoader::kMaxCatalogBytes` (32,768 bytes), each file for itself**; a larger file is skipped with an `OversizedFile` diagnostic. The reason is memory: a small device must not load unlimited text from the card. The limit is the owner's decision (raised from 16,384 to 32,768 bytes on 2026-10-06; the device has 8 MB of PSRAM; `scripts/check_i18n.py` prints the size of every shipped catalog).
- `lang/en.toml` and `lang/web/en.toml` are the files a translator starts from, so each must stay under the limit: a test fails when it does not (`test_the_english_catalog_fits_what_a_catalog_on_the_card_may_have`, and the same for the page's), others that each is accepted whole under a new code, and `check_i18n.py` fails too. A key that only host code uses does not belong in `lang/`: `check_i18n.py --usage` says so, and also when a key of the device set is used only by the web code (`src/web/`, `scripts/gen_web.py`, `config/schema.toml`) or a key of the web set only by device code: it is in the wrong file. `check_i18n.py` prints the size of every shipped catalog against the limit; all six fit ([translating.md](../translating.md) has the numbers).
- **Memory.** Before the split each shipped catalog was 21 to 25 KB, about 40 % of it the page's words that the device never shows on its own screen. Now the device set is 13 to 15 KB per language and the web set 8 to 10 KB. Parsed into memory (measured on a 64-bit host with the real parser: a map of strings per key, malloc overhead included, so the device's 32-bit figures are lower) the three device catalogs take about 128 KB (files 42.6 KB) and the three web catalogs about 66 KB (files 28.6 KB), so before the split the device carried about 194 KB of which a third was never shown on its own screen. Keeping the page's catalogs loaded costs those 66 KB all the time; loading on demand costs nothing while Wi-Fi is off and a read of three small files (and the card's) each time the page is opened. The shipped behaviour is on demand, released with the page; keeping them loaded is a one-line change in `WebService::poll` (do not call `pageGone()`).


## Rules for code that shows text

- Every text the user reads comes from a catalog — never from a string literal in the code.
- A message that contains a number of things (messages, minutes) is a plural message.
- Layouts must cope with the longest language: German and French run 20–40 % longer than English.
- Only characters the display fonts can draw may appear in catalogs; `scripts/check_i18n.py` rejects anything outside `assets/fonts/charset.txt` (Latin-1, `Œ œ Ÿ €` and the interface symbols; see [ui-text.md](../ui/ui-text.md)). `scripts/check_i18n.py --usage` checks the other direction: every key is used by the code or a test, and no string in the code looks like a catalog key that does not exist.
- Messages whose key starts with `sms.` are sent as text messages and may use only the GSM 7-bit alphabet (no ê, ç, typographic quotes): any other character makes the SMS 70 characters per part instead of 160. `scripts/check_i18n.py` rejects them.

## Checks

```bash
pio test -e native              # parser, translator, plural rules, shipped catalogs
python3 scripts/check_i18n.py   # the device set, the web set and the host sets: same keys, same placeholders, right plural forms, drawable characters (device); every file's size against the limit
python3 test/test_check_i18n/test_check.py   # the check itself: a key in the wrong set, in both sets, a missing file, the limit
python3 scripts/check_i18n.py --usage   # every key is used; no unknown key in the code
```
